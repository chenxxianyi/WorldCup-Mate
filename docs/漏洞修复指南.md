# WorldCup Mate 漏洞修复指南

本文档基于当前项目代码的静态安全审计结果整理，目标是帮助开发者按优先级修复真实可被利用的风险。文档只描述防御思路和修复方案，不提供攻击利用步骤。

## 修复优先级总览

| 优先级 | 风险点 | 主要影响 | 建议处理 |
| --- | --- | --- | --- |
| P0 | 公开 AI 生成接口可被匿名滥用 | AI 成本被刷、服务被拖慢、数据库写入膨胀 | 登录保护、游客只读缓存、IP/用户限流 |
| P0 | 密钥、默认口令和服务端口暴露 | 凭据泄露、数据库/Redis 被直接攻击 | 轮换密钥、收紧 Docker 暴露、使用生产 Secret |
| P1 | 登录/注册缺少防爆破 | 撞库、弱口令爆破、批量注册 | 增加账号+IP 限流、失败延迟、审计日志 |
| P1 | 前端明文记住密码 | 本地密码泄露、XSS 后直接失陷 | 删除明文保存密码，改用浏览器密码管理器 |
| P1 | 通知标记已读存在越权 | 任意登录用户可修改他人通知状态 | 更新时校验 `user_id` |
| P2 | JWT 校验和失效机制不完整 | Token 被盗后长期有效、算法防御不足 | 固定算法、增加失效版本或黑名单 |
| P2 | 上传资源静态暴露缺少安全头 | 内容嗅探、缓存和跨域资源风险 | 增加安全响应头、限制格式或转码 |

## P0：公开 AI 生成接口可被匿名滥用

### 相关位置

- `backend/internal/routes/router.go`
  - `/api/ai/match-insight`
  - `/api/ai/today-recommendations`
  - `/api/ai/group-analysis`
  - `/api/ai/explain`
  - `/api/ai/share-copy`
  - `/api/matches/:id/post-match-summary/generate`
- `backend/internal/services/ai_service.go`
  - `checkLimit` 在 `userID == nil` 时直接放行
- `backend/internal/handlers/post_match_summary_handler.go`
  - `GET /api/matches/:id/post-match-summary` 当前也会调用生成逻辑

### 风险说明

当前 AI 生成接口大多是公开路由，游客可以不登录直接触发模型调用。`checkLimit` 只限制登录用户，游客没有每日额度限制。这会导致：

- AI API 费用被恶意刷高。
- 大量并发请求拖慢后端服务。
- `ai_generated_contents` 和 `ai_usage_logs` 等表快速膨胀。
- `force_refresh` 被滥用，绕过缓存反复生成。

### 修复方案

1. 将所有会真实调用 AI 的生成接口移入 `JWTAuth` 路由组。
2. 允许游客访问的接口只能读取已存在缓存或数据库结果，不能触发模型调用。
3. `GET /post-match-summary` 改为纯读取接口：只查 Redis/DB，有则返回，无则返回空状态。
4. `POST /post-match-summary/generate` 只允许登录用户或管理员调用。
5. 在中间件层增加 Redis 限流：
   - 按 IP 限制游客请求。
   - 按用户 ID 限制登录用户请求。
   - 对 AI 接口设置更严格额度。
6. `force_refresh` 建议只允许管理员或有限次数的登录用户使用。

### 建议验收标准

- 未登录用户调用 AI 生成接口返回 `401`。
- 未登录用户访问赛后摘要 GET 不会产生新的 AI usage log。
- 同一 IP 高频请求 AI 接口会返回 `429`。
- 登录用户超出每日 AI 使用额度后会返回明确错误。

## P0：密钥、默认口令和服务端口暴露

### 相关位置

- `.env`
- `docker-compose.yml`
- `backend/Dockerfile`

### 风险说明

当前根目录 `.env` 出现真实形态 API key；`docker-compose.yml` 中存在弱默认 MySQL root 密码、默认 JWT secret，并且 MySQL/Redis 端口映射到了宿主机。`backend/Dockerfile` 还会把 `.env` 复制进镜像。

这些问题会导致：

- API key 泄露后被第三方滥用。
- JWT secret 弱或泄露后，攻击者可伪造登录身份。
- MySQL/Redis 暴露到公网后可能被扫描和爆破。
- 镜像分发或泄露时同时泄露环境变量。

### 修复方案

1. 立即轮换所有已经出现在仓库或本机 `.env` 中的真实密钥。
2. 保持 `.env` 不进入 Git；仓库只保留 `.env.example`。
3. 从 `backend/Dockerfile` 删除 `COPY --from=builder /app/.env ./.env`。
4. 生产环境用环境变量、Docker Secret、Kubernetes Secret 或云厂商 Secret Manager 注入密钥。
5. 修改 `docker-compose.yml`：
   - MySQL 和 Redis 不对宿主机公开端口，除非本地开发需要。
   - Redis 设置密码。
   - MySQL 使用强随机密码。
   - 后端数据库账号使用最小权限，不使用 root。
6. `JWT_SECRET` 使用至少 32 字节随机字符串，并定期轮换。

### 建议验收标准

- 镜像中不存在 `.env` 文件。
- 生产服务器公网只暴露前端入口或反向代理端口。
- MySQL/Redis 只能被内部网络访问。
- `APP_ENV=production` 时，默认或弱 `JWT_SECRET` 无法启动服务。

## P1：登录/注册缺少防爆破

### 相关位置

- `backend/internal/handlers/auth_handler.go`
- `backend/internal/services/auth_service.go`
- `backend/internal/routes/router.go`

### 风险说明

登录和注册接口目前没有频率限制、失败延迟、验证码或账号锁定策略。攻击者可以批量尝试常见密码，或者针对管理员账号进行撞库。

### 修复方案

1. 增加认证限流中间件：
   - 登录：按 `IP + account` 限制。
   - 注册：按 IP 限制。
   - 管理员登录：使用更严格阈值。
2. 连续失败后增加短暂锁定或指数退避。
3. 对管理员账号启用更强密码策略和二次验证。
4. 记录登录失败日志，包含 IP、账号、时间、User-Agent。
5. 禁止返回过于具体的账号存在性信息，避免枚举用户。

### 建议验收标准

- 同一账号连续失败多次后短时间内无法继续尝试。
- 登录失败日志可用于排查异常来源。
- 管理员登录接口有独立限流策略。

## P1：前端明文保存密码

### 相关位置

- `frontend/src/pages/user/LoginPage.vue`

### 风险说明

当前“记住密码”会把账号和密码明文写入 `localStorage`。如果浏览器环境被 XSS、恶意插件、共享电脑或本地恶意软件影响，密码会被直接读取。

### 修复方案

1. 删除“记住密码”功能，不再保存明文密码。
2. 保留浏览器原生密码管理器能力，例如正确设置：
   - 登录账号输入框：`autocomplete="username"`
   - 密码输入框：`autocomplete="current-password"`
   - 注册密码：`autocomplete="new-password"`
3. “自动登录”只保存 token，不保存密码。
4. 更推荐后续将 token 改为 HttpOnly、Secure、SameSite Cookie，降低 XSS 读取 token 的风险。

### 建议验收标准

- 登录成功后 `localStorage` 中不再出现用户明文密码。
- 刷新页面后仍可依赖 token 保持登录状态。
- 浏览器密码管理器仍能正常提示保存密码。

## P1：通知标记已读存在越权

### 相关位置

- `backend/internal/handlers/notification_handler.go`
- `backend/internal/services/notification_service.go`
- `backend/internal/repositories/notification_repo.go`

### 风险说明

单条通知标记已读时，目前只按通知 ID 更新，没有校验通知是否属于当前用户。任意登录用户只要猜到通知 ID，就能把其他用户的通知改成已读。

### 修复方案

1. Handler 中读取当前 `user_id`。
2. Service 和 Repository 方法签名改为 `MarkNotificationRead(userID, id uint)`。
3. SQL 条件改为 `WHERE id = ? AND user_id = ?`。
4. 检查 `RowsAffected`，如果为 0，返回 `not found` 或 `unauthorized`。

### 修复示例

```go
func MarkNotificationRead(userID, id uint) error {
	result := database.DB.Model(&models.Notification{}).
		Where("id = ? AND user_id = ?", id, userID).
		Update("is_read", true)
	if result.Error != nil {
		return result.Error
	}
	if result.RowsAffected == 0 {
		return gorm.ErrRecordNotFound
	}
	return nil
}
```

### 建议验收标准

- 用户 A 不能标记用户 B 的通知。
- 用户只能操作自己的通知。
- 越权请求返回 `404` 或 `403`。

## P2：JWT 校验和失效机制

### 相关位置

- `backend/internal/utils/jwt.go`
- `backend/internal/middleware/jwt.go`

### 风险说明

当前 JWT 使用 HS256 签名，但解析时没有显式限制签名算法；同时登出只是前端清理 token，后端没有吊销机制。Token 一旦泄露，在过期前仍可继续使用。

### 修复方案

1. 在 `ParseToken` 中显式校验算法：

```go
if t.Method != jwt.SigningMethodHS256 {
	return nil, jwt.ErrTokenSignatureInvalid
}
```

2. Claims 增加 `Issuer`、`Audience`、`ID` 等字段，并在解析时校验。
3. 用户表增加 `token_version` 或 `password_changed_at`。
4. 改密、封禁、登出时使旧 token 失效。
5. 管理员 token 缩短有效期。

### 建议验收标准

- 非 HS256 算法 token 被拒绝。
- 修改密码后旧 token 立即失效。
- 管理员 token 生命周期短于普通用户。

## P2：上传资源静态暴露缺少安全头

### 相关位置

- `backend/internal/services/auth_service.go`
- `backend/cmd/server/main.go`
- `frontend/nginx.conf`

### 风险说明

头像上传已经做了扩展名、大小和 MIME 头检测，这是好的基础。但上传目录被静态暴露，如果缺少安全响应头，仍可能出现内容嗅探、缓存策略不当或资源滥用问题。

### 修复方案

1. 对 `/uploads` 增加响应头：
   - `X-Content-Type-Options: nosniff`
   - `Cache-Control` 根据业务设置
   - 可选 `Content-Disposition`
2. 只允许必要图片格式，建议优先保留 `jpg/png/webp`，谨慎允许 `gif`。
3. 上传后统一转码为安全格式并剥离元数据。
4. 上传文件放到独立对象存储域名，不携带主站 Cookie。
5. 增加用户上传频控和总容量限制。

### 建议验收标准

- 上传非图片内容会被拒绝。
- 上传资源响应包含 `nosniff`。
- 大量上传会被限流。

## 其他加固建议

### 安全响应头

建议在 Nginx 或 Gin 中统一增加：

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

如果后续需要更强 XSS 防护，可逐步引入 CSP：

```nginx
add_header Content-Security-Policy "default-src 'self'; img-src 'self' data: https:; connect-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self';" always;
```

### 日志和监控

建议记录并告警：

- 登录失败次数异常。
- AI 接口调用量突增。
- 单 IP 请求量突增。
- 管理后台接口调用异常。
- 数据库连接失败或 Redis 限流失败。

### 数据库安全

建议：

- 生产数据库账号最小权限。
- 开启定期备份。
- 不把数据库端口暴露到公网。
- 重要表增加审计字段。
- 管理操作写入审计日志。

## 推荐修复顺序

1. 轮换 `.env` 中出现过的真实密钥，移除镜像内 `.env`。
2. 收紧 `docker-compose.yml`，避免 MySQL/Redis 暴露到公网。
3. 将 AI 生成接口改为登录访问，并增加 Redis 限流。
4. 将赛后摘要 GET 改为纯缓存/DB 读取。
5. 删除前端明文保存密码逻辑。
6. 修复通知标记已读的 `user_id` 越权问题。
7. 增加登录/注册/管理员登录限流。
8. 加强 JWT 校验和 token 失效机制。
9. 增加上传资源安全头和上传频控。
10. 补充安全测试和异常监控。

## 建议增加的安全测试

- 未登录用户调用 AI 生成接口应返回 `401`。
- 游客访问赛后摘要 GET 不应产生新的 AI 调用记录。
- 同一 IP 高频调用登录接口应被限制。
- 用户不能标记其他用户的通知为已读。
- 修改密码后旧 token 不能继续访问受保护接口。
- 上传伪装成图片的非图片文件应被拒绝。
- 生产配置缺少强 `JWT_SECRET` 时服务应启动失败。
