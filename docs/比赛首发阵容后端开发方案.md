# WorldCup Mate 比赛首发阵容后端开发方案

## 1. 后端目标

为比赛详情页提供统一、稳定的首发阵容数据能力。

第一阶段目标：

- 使用 football-data.org 的 match detail 接口同步首发、替补和阵型。
- 保存到本地 `match_lineups`、`match_lineup_players`。
- 提供用户端接口 `GET /api/matches/:id/lineups`。
- 阵容未公布或第三方返回空时，不清空已有阵容。

第二阶段目标：

- 接入 API-Football `fixtures/lineups`。
- 建立本地比赛与 API-Football fixture id 的映射。
- 保存 `grid` 站位、教练、头像关联和更完整的阵容数据。
- API-Football 不可用时回退 football-data 阵容。

## 3. 数据源策略

### 3.1 第一阶段：football-data

接口：

```http
GET https://api.football-data.org/v4/matches/{match_id}
Header: X-Auth-Token: {FOOTBALL_DATA_API_KEY}
```

使用原因：

- 当前项目已有 football-data 比赛 ID。
- 不需要新增 fixture 映射即可同步。
- 可以快速得到阵型、首发名单和替补名单。

局限：

- 通常没有球员头像。
- 不一定提供站位坐标。
- 球员 ID 与 API-Football 不一致。

### 3.2 第二阶段：API-Football

接口：

```http
GET https://v3.football.api-sports.io/fixtures/lineups?fixture={fixture_id}
Header: x-apisports-key: {API_FOOTBALL_KEY}
```

使用原因：

- 提供 `grid` 站位字段。
- 提供教练、首发、替补、号码、位置。
- 可以和已有 API-Football 球员大名单、头像数据关联。

局限：

- 需要先建立本地比赛与 API-Football fixture id 的映射。
- 有请求额度限制。
- 正式首发通常只会在赛前几十分钟公布。

## 9. 第一阶段同步流程

`SyncMatchLineups` 使用 football-data：

1. 查询本地 `matches`。
2. 检查 `external_provider == football-data` 且 `external_id` 不为空。
3. 请求 football-data match detail。
4. 读取 `homeTeam.formation / lineup / bench`。
5. 读取 `awayTeam.formation / lineup / bench`。
6. 转换为 `MatchLineup` 和 `MatchLineupPlayer`。
7. 根据 `match_id + team_id` upsert 阵容头。
8. 有首发或替补时，事务替换该队阵容球员。
9. 没有阵容时，只更新状态，不清空旧球员。

状态判断：

- 首发人数大于等于 11：`available`
- 首发人数大于 0 但不足 11：`partial`
- 首发和替补均为空：`unavailable`

## 10. 第二阶段同步流程

`SyncAPIFootballMatchLineups` 使用 API-Football：

1. 查询本地比赛。
2. 查询 `external_match_mappings` 中 `provider = api-football` 的映射。
3. 如果映射不存在，调用 `EnsureAPIFootballMatchMapping` 自动匹配。
4. 调用 `fixtures/lineups?fixture={fixture_id}`。
5. 保存阵型、教练、首发、替补、`grid`。
6. 通过 `source_player_id` 优先关联 `players.source = api-football` 的球员。
7. 关联不到时尝试 `team_id + name_en` 弱匹配。
8. 仍关联不到时 `player_id = nil`，保留第三方返回姓名。
9. API-Football 有完整阵容时，将该队 `source` 设为 `api-football`。
10. API-Football 无数据或失败时保留 football-data 阵容。

自动匹配 fixture 建议：

1. 读取主队、客队的 `ExternalTeamMapping(provider=api-football)`。
2. 按比赛日期和主队 external id 查询 API-Football fixtures。
3. 比对主客队 external id。
4. 比对开球时间，允许 2 小时以内误差。
5. 多个候选时选择时间最接近的一场。
6. 写入 `ExternalMatchMapping`，`matched_by = auto_date_team_time`。

必须保留后台手动修正能力，因为自动匹配错误会导致整场阵容错位。

## 11. 球员匹配和中文名策略

匹配优先级：

1. `source = api-football + source_player_id`
2. `team_id + name_en` 标准化匹配
3. `team_id + shirt_number + position`
4. 不匹配本地球员，只展示阵容接口返回数据

展示名策略：

- 如果关联到本地 `players`，优先使用 `players.name`、`players.name_en`、`players.photo_url`。
- 如果没有关联到本地 `players`，使用第三方返回的 `player.name`。
- 可复用现有 `services.LocalizePlayerName(...)` 做中文名转换。
- 不生成虚假中文名、虚假头像或虚假号码。

位置标准化：

| Provider position | position | position_label |
| --- | --- | --- |
| `G` / `GK` / `Goalkeeper` | `GK` | `门将` |
| `D` / `DF` / `Defender` | `DF` | `后卫` |
| `M` / `MF` / `Midfielder` | `MF` | `中场` |
| `F` / `FW` / `Attacker` | `FW` | `前锋` |

如果 provider 未返回位置，字段保持空，不补猜测值。

## 14. 定时任务

新增：

```text
backend/internal/jobs/lineup_syncer.go
```

同步窗口：

```text
kickoff_time_utc - 90min <= now <= kickoff_time_utc + 30min
```

推荐节奏：

- 非比赛窗口：不跑阵容同步。
- 开赛前 90-45 分钟：每 15 分钟查一次。
- 开赛前 45 分钟到开赛后 15 分钟：每 5-10 分钟查一次。
- 比赛进行中：每 15 分钟查一次，直到阵容状态为 `available`。
- 比赛结束后补查一次。

节流策略：

- 每次只同步临近比赛。
- 每场比赛之间 sleep 1-2 秒。
- API-Football 额度不足时只跑 football-data。
- 已经有 `api-football` 完整阵容的比赛停止高频请求。

## 17. 错误和降级策略

- 阵容未公布：返回 `status = unavailable`，不算系统错误。
- football-data 失败：记录错误，不影响比赛详情页。
- API-Football 映射缺失：先展示 football-data 阵容。
- API-Football 请求限流：停止增强同步，保留已有阵容。
- 第三方返回空阵容：不删除旧阵容。
- 球员无法匹配本地 `players`：仍展示第三方球员名。
- API key 未配置：管理端同步接口返回明确错误，定时任务跳过。

## 18. 开发步骤

### P0：数据库和查询接口

7. 空阵容时返回 `status = unavailable`。

### P1：football-data 首发列表版

1. 增强 football-data provider，支持单场 match detail。
2. 实现 `SyncMatchLineups`。
3. 实现 `POST /api/admin/matches/:id/sync-lineups`。
4. 保存阵型、首发、替补。

## 19. 后端验收标准

第一阶段验收：

- 数据库存在 `match_lineups` 和 `match_lineup_players`。
- 管理员可手动同步某场比赛阵容。
- `GET /api/matches/:id/lineups` 可返回统一结构。
- 阵容未公布时返回 `status = unavailable`。
- 第三方空响应不会清空已有阵容。
- `go test ./...` 通过。
- `go build ./...` 通过。

第二阶段验收：

- 数据库存在 `external_match_mappings`。
- 本地比赛可匹配 API-Football fixture id。
- 可同步 API-Football lineups。
- 首发球员包含 `grid`。
- 阵容球员尽量关联本地 `players`。
- API-Football 不可用时自动回退 football-data 阵容。
- 请求限流时不会持续高频重试。

## 20. 风险和注意事项

- 正式首发通常在赛前几十分钟才公布，提前数天为空是正常情况。
- football-data 与 API-Football 的球员 ID 不一致，不能混用同一个 `source_player_id`。
- API-Football fixture 自动匹配必须谨慎，建议保留后台人工修正。
- API-Football 额度有限，不能全量高频扫描所有比赛。
- 阵容发布后仍可能临场调整，开赛前后短时间内需要刷新。
- 后端统一写入本地表，前端不直接请求第三方接口。
