# WorldCup Mate 比赛首发阵容同步与展示方案

## 1. 目标

为比赛详情页增加“首发阵容 / 替补席 / 阵型站位”能力，在比赛开始前后自动获取两队阵容信息，并在用户端展示。

本方案合并两个版本：

- 第一阶段：使用 `football-data.org` 快速落地首发与替补列表。
- 第二阶段：接入 `API-Football / API-SPORTS` 的 lineups 数据，完成阵型站位图和更完整的阵容展示。

最终目标是第二阶段效果，但第一阶段的数据库、接口和前端结构要直接服务于第二阶段，避免后续推倒重做。

## 2. 数据源结论

### 2.1 football-data.org

当前项目已经使用 football-data.org 同步世界杯赛程，且 `matches` 表已经保存：

- `external_provider = football-data`
- `external_id = football-data match id`

football-data 的比赛详情数据中包含：

- `homeTeam.formation`
- `homeTeam.lineup`
- `homeTeam.bench`
- `awayTeam.formation`
- `awayTeam.lineup`
- `awayTeam.bench`

适合第一阶段快速实现：

- 不需要新增比赛 ID 映射。
- 复用当前 `FOOTBALL_DATA_API_KEY`。
- 可以先完成首发名单、替补名单、阵型文字展示。

局限：

- 通常没有球员头像。
- 不一定提供球场站位坐标。
- 球员 ID 与 API-Football 球员 ID 不完全一致。

官方文档：

```text
https://docs.football-data.org/general/v4/match.html
```

### 2.2 API-Football / API-SPORTS

API-Football 提供专门的阵容接口：

```http
GET https://v3.football.api-sports.io/fixtures/lineups?fixture={fixture_id}
Header: x-apisports-key: {API_FOOTBALL_KEY}
```

返回能力包括：

- 阵型 `formation`
- 教练 `coach`
- 首发 `startXI`
- 替补 `substitutes`
- 球员号码、位置
- `grid` 站位字段，可用于球场阵型图

适合第二阶段实现完整体验：

- 可绘制 4-3-3、3-4-2-1 等阵型站位。
- 能和现有 API-Football 球员大名单、头像数据组合展示。
- 数据结构更适合“比赛开始时阵容”场景。

局限：

- 当前项目的比赛 ID 来自 football-data，不是 API-Football fixture id。
- 需要新增本地比赛与 API-Football fixture 的映射。
- API-Football 有请求额度限制，同步策略必须节流。

官方文档：

```text
https://www.api-football.com/documentation-v3#operation/get-fixtures-lineups
```

## 3. 总体路线

### 阶段 A：首发阵容列表版

目标：

- 比赛详情页能展示两队首发、替补、阵型。
- 使用 football-data match id 直接同步。
- 不做球场站位图。

完成后用户能看到：

- 阵型：如 `4-3-3`
- 首发 11 人
- 替补球员
- 阵容未发布状态

### 阶段 B：阵型站位增强版

目标：

- 新增 API-Football fixture 映射。
- 使用 API-Football `fixtures/lineups` 获取 `grid`。
- 比赛详情页增加球场阵型图。
- 优先关联现有 `players` 表，展示中文名、头像、号码、位置。

完成后用户能看到：

- 球场可视化站位图
- 左右两队阵型对照
- 首发球员头像/号码/中文名
- 替补席列表
- 教练信息

## 4. 数据库设计

### 4.1 新增 match_lineups 表

保存每场比赛每支球队的阵容头信息。

```go
type MatchLineup struct {
	ID              uint           `gorm:"primaryKey" json:"id"`
	MatchID         uint           `gorm:"uniqueIndex:idx_match_team_lineup;not null" json:"match_id"`
	Match           Match          `gorm:"foreignKey:MatchID" json:"match,omitempty"`
	TeamID          uint           `gorm:"uniqueIndex:idx_match_team_lineup;index;not null" json:"team_id"`
	Team            Team           `gorm:"foreignKey:TeamID" json:"team,omitempty"`
	Side            string         `gorm:"size:10;index;not null" json:"side"`
	Formation       string         `gorm:"size:20" json:"formation"`
	CoachName       string         `gorm:"size:100" json:"coach_name"`
	CoachNameEn     string         `gorm:"size:100" json:"coach_name_en"`
	Source          string         `gorm:"size:50;index;not null" json:"source"`
	SourceMatchID   string         `gorm:"size:100;index" json:"source_match_id"`
	ExternalTeamID  string         `gorm:"size:100;index" json:"external_team_id"`
	Status          string         `gorm:"size:20;default:unavailable;index" json:"status"`
	LastSyncedAt    *time.Time     `json:"last_synced_at"`
	CreatedAt       time.Time      `json:"created_at"`
	UpdatedAt       time.Time      `json:"updated_at"`
	DeletedAt       gorm.DeletedAt `gorm:"index" json:"-"`
}
```

字段说明：

- `side`：`home` / `away`
- `status`：`unavailable` / `partial` / `available`
- `source`：`football-data` 或 `api-football`
- `SourceMatchID`：第三方比赛 ID
- `ExternalTeamID`：第三方球队 ID

### 4.2 新增 match_lineup_players 表

保存首发和替补球员。

```go
type MatchLineupPlayer struct {
	ID              uint           `gorm:"primaryKey" json:"id"`
	MatchLineupID   uint           `gorm:"index;not null" json:"match_lineup_id"`
	MatchLineup     MatchLineup    `gorm:"foreignKey:MatchLineupID" json:"lineup,omitempty"`
	MatchID         uint           `gorm:"index;not null" json:"match_id"`
	TeamID          uint           `gorm:"index;not null" json:"team_id"`
	PlayerID        *uint          `gorm:"index" json:"player_id"`
	Player          *Player        `gorm:"foreignKey:PlayerID" json:"player,omitempty"`
	Source          string         `gorm:"size:50;index;not null" json:"source"`
	SourcePlayerID  string         `gorm:"size:100;index" json:"source_player_id"`
	Name            string         `gorm:"size:100;not null" json:"name"`
	NameEn          string         `gorm:"size:100" json:"name_en"`
	ShirtNumber     int            `gorm:"index" json:"shirt_number"`
	Position        string         `gorm:"size:20;index" json:"position"`
	PositionLabel   string         `gorm:"size:20" json:"position_label"`
	Role            string         `gorm:"size:20;index;not null" json:"role"`
	Grid            string         `gorm:"size:20" json:"grid"`
	SortOrder       int            `gorm:"index" json:"sort_order"`
	PhotoURL        string         `gorm:"size:500" json:"photo_url"`
	CreatedAt       time.Time      `json:"created_at"`
	UpdatedAt       time.Time      `json:"updated_at"`
	DeletedAt       gorm.DeletedAt `gorm:"index" json:"-"`
}
```

字段说明：

- `role`：`start_xi` / `substitute`
- `grid`：API-Football 的站位字段，例如 `2:3`
- `PlayerID`：尽量关联本地 `players.id`，匹配不到允许为空
- `Name`：页面展示名，沿用中文化逻辑
- `NameEn`：第三方原始英文名

### 4.3 新增 external_match_mappings 表

第二阶段需要保存本地比赛与 API-Football fixture 的映射。

```go
type ExternalMatchMapping struct {
	ID                uint      `gorm:"primaryKey" json:"id"`
	MatchID           uint      `gorm:"uniqueIndex:idx_provider_match;not null" json:"match_id"`
	Match             Match     `gorm:"foreignKey:MatchID" json:"match,omitempty"`
	Provider          string    `gorm:"uniqueIndex:idx_provider_match;size:50;not null" json:"provider"`
	ExternalMatchID   string    `gorm:"size:100;index;not null" json:"external_match_id"`
	ExternalHomeID    string    `gorm:"size:100;index" json:"external_home_id"`
	ExternalAwayID    string    `gorm:"size:100;index" json:"external_away_id"`
	ExternalHomeName  string    `gorm:"size:100" json:"external_home_name"`
	ExternalAwayName  string    `gorm:"size:100" json:"external_away_name"`
	MatchedBy         string    `gorm:"size:50" json:"matched_by"`
	CreatedAt         time.Time `json:"created_at"`
	UpdatedAt         time.Time `json:"updated_at"`
}
```

用途：

- 本地 `matches.id` 与 API-Football fixture id 建立关系。
- 后续调用 `fixtures/lineups` 必须依赖该映射。
- 可通过日期 + 双方球队映射 + 比赛时间自动匹配，也允许后台手动维护。

### 6.1 第一阶段同步流程

1. 根据本地 `matchID` 查询 `matches`。
2. 检查 `match.external_provider == football-data` 且 `external_id` 不为空。
3. 请求 football-data match detail。
4. 读取 `homeTeam.formation / lineup / bench`。
5. 读取 `awayTeam.formation / lineup / bench`。
6. 转换为本地 `match_lineups` 和 `match_lineup_players`。
7. 根据 `match_id + team_id` upsert 阵容头。
8. 根据 `lineup_id + role + source_player_id` 或 `lineup_id + role + shirt_number + name` upsert 阵容球员。
9. 如果第三方没有返回阵容，不清空旧数据，只更新状态为 `unavailable`。

### 6.2 第二阶段同步流程

1. 根据本地 `matchID` 查询 API-Football fixture 映射。
2. 如果没有映射，尝试自动匹配：
   - 读取本地 home / away team 的 API-Football team mapping。
   - 用比赛日期和球队 ID 查询 API-Football fixtures。
   - 比对主客队、开球时间，找到最接近的一场。
   - 写入 `external_match_mappings`。
3. 调用 `fixtures/lineups?fixture={fixture_id}`。
4. 保存 `formation / coach / startXI / substitutes / grid`。
5. 用 `source_player_id` 优先关联 `players.source = api-football` 的球员。
6. 关联不到时用 `team_id + name_en` 弱匹配。
7. 仍然匹配不到时 `player_id = null`，但保留第三方返回的名字。
8. 如果 API-Football 返回成功，覆盖同场同队的展示数据源为 `api-football`。
9. 如果 API-Football 没有数据，保留 football-data 阵容。

## 9. 定时任务设计

新增：

```text
backend/internal/jobs/lineup_syncer.go
```

同步窗口：

- 当前时间前 30 分钟到后 90 分钟的比赛。
- 即 `kickoff_time_utc - 90min <= now <= kickoff_time_utc + 30min`。

推荐节奏：

- 非比赛窗口：不跑阵容同步。
- 开赛前 90-45 分钟：每 15 分钟查一次。
- 开赛前 45 分钟到开赛后 15 分钟：每 5-10 分钟查一次。
- 比赛进行中：每 15 分钟查一次，直到阵容状态为 `available`。
- 比赛结束后：补查一次。

节流策略：

- 每次只同步临近比赛。
- 每场比赛同步之间 sleep 1-2 秒。
- API-Football 额度不足时降级只用 football-data。
- 如果某场已经有 `api-football` 完整阵容，则不再高频请求。

## 11. 球员匹配与中文名策略

优先级：

1. `source = api-football + source_player_id`
2. `team_id + name_en` 标准化匹配
3. `team_id + shirt_number + position`
4. 不匹配本地球员，只展示阵容接口返回数据

中文名：

- 复用现有 `services.LocalizePlayerName(...)`。
- `name` 保存中文展示名。
- `name_en` 保存第三方原名。
- 如果 API-Football 阵容球员能关联 `players`，优先使用 `players.name` 和 `players.photo_url`。

## 12. 同步状态

复用 `sync_states`：

```text
provider = football-data / api-football
resource = lineups
status = running / success / failed
```

建议记录：

- 最近同步时间
- 最近错误
- 下次同步时间
- 本次成功场次数
- 本次阵容可用场次数

## 13. 错误和降级策略

- 阵容未公布：接口返回 `status = unavailable`，前端显示占位文案。
- football-data 失败：记录错误，不影响比赛详情页其他信息。
- API-Football 映射缺失：先展示 football-data 阵容。
- API-Football 请求限流：停止增强同步，保留已有阵容。
- 第三方返回空阵容：不删除旧阵容。
- 球员无法匹配本地 `players`：仍展示第三方球员名。

- 可同步 API-Football lineups。
- 首发球员包含阵型站位 `grid`。
- 比赛详情页可展示球场站位图。
- API-Football 不可用时自动回退 football-data 阵容。
- 不会因为第三方空响应清空已有阵容。

## 16. 风险和注意事项

- 世界杯正式比赛前，第三方阵容接口可能长期为空，这是正常现象。
- 首发阵容通常在赛前几十分钟才发布，不能期望提前几天拿到。
- football-data 与 API-Football 的球员 ID 不同，不能强依赖同一个 `source_player_id`。
- API-Football 额度有限，必须做临近比赛同步，不能频繁全量扫。
- API-Football fixture 自动匹配要谨慎，建议保留后台手动修正能力。
- 阵容发布后仍可能临场调整，比赛开始前后需要短时间高频刷新。

## 17. 推荐最终实现形态

最终生产方案建议：

1. football-data 作为基础阵容源，保证有比赛 ID 就能尝试同步。
2. API-Football 作为增强阵容源，负责站位图、grid、与球员头像联动。
3. 用户端统一读本地 `match_lineups`，不直接请求第三方。
4. 同步层按优先级写入：
   - API-Football 完整阵容优先展示。
   - football-data 阵容作为兜底。
5. 前端统一接口，不关心数据来自哪个 provider。
