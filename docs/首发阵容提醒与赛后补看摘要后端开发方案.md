# WorldCup Mate 首发阵容提醒与赛后补看摘要后端开发方案

## 1. 目标

基于现有 `reminders`、`notifications`、`match_lineups`、`AIGeneratedContent` 和定时任务能力，实现两个个人自用功能：

1. 首发阵容提醒：比赛首发阵容同步可用后，给相关用户发送一次站内通知。
2. 赛后补看摘要：比赛结束后生成 AI 摘要，并可通知相关用户查看。

第一版优先站内通知，不强依赖邮件、Web Push 或消息队列。

## 2. 实现范围

### P0 必做

- 扩展通知跳转字段。
- 新增用户比赛事件去重表。
- 实现首发阵容提醒扫描任务。
- 实现赛后摘要手动生成接口。
- 复用 AI 生成内容缓存。

### P1 增强

- 赛后摘要自动生成任务。
- 赛后摘要通知。
- 关注球队用户也接收首发/赛后通知。
- 免剧透模式联动。

## 5. 首发阵容提醒后端设计

### 5.1 Service

新增文件：

```text
backend/internal/services/lineup_alert_service.go
```

核心方法：

```go
func ScanAndSendLineupAlerts(ctx context.Context) error
func SendLineupAlertForMatch(ctx context.Context, matchID uint) error
```

### 5.2 扫描比赛范围

扫描条件：

```text
kickoff_time_utc >= now - LINEUP_ALERT_WINDOW_AFTER_MINUTES
kickoff_time_utc <= now + LINEUP_ALERT_WINDOW_BEFORE_MINUTES
status NOT IN finished, cancelled
```

推荐配置：

```env
LINEUP_ALERT_ENABLED=true
LINEUP_ALERT_SCAN_INTERVAL_SECONDS=120
LINEUP_ALERT_WINDOW_BEFORE_MINUTES=120
LINEUP_ALERT_WINDOW_AFTER_MINUTES=30
```

### 5.3 阵容可用判断

第一版推荐严格判断：

- 主队存在 lineup。
- 客队存在 lineup。
- 双方 `start_xi` 数量都 >= 11。

可封装：

```go
func isLineupAlertReady(lineups []models.MatchLineup) bool
```

如果第三方只返回一方阵容，可暂不提醒，避免误报。

### 5.4 通知目标用户

候选用户来源：

1. 收藏该比赛的用户。
2. 设置过该比赛提醒的用户。
3. P1：关注主队或客队的用户。

合并后去重：

```go
map[uint]bool
```

### 5.5 通知创建流程

对每个用户：

1. 查询 `UserMatchEventLog` 是否存在：
   - `event_type = lineup_available`
2. 不存在则创建通知：

```go
notification := &models.Notification{
	UserID:     userID,
	Title:      fmt.Sprintf("首发已公布：%s vs %s", match.HomeTeam.Name, match.AwayTeam.Name),
	Content:    "双方首发阵容已更新，点击查看阵型和首发名单。",
	Type:       "lineup",
	TargetType: "match",
	TargetID:   match.ID,
}
```

3. 创建 `UserMatchEventLog`。

建议在同一个事务里完成通知和 event log，避免通知已发但去重记录失败。

### 5.6 Job

新增文件：

```text
backend/internal/jobs/lineup_alert_scanner.go
```

实现：

```go
func StartLineupAlertScanner() {
	if !services.IsLineupAlertEnabled() {
		log.Println("Lineup alert scanner disabled")
		return
	}

	go func() {
		ticker := time.NewTicker(services.NextLineupAlertInterval())
		defer ticker.Stop()

		for {
			runLineupAlertScan()
			<-ticker.C
		}
	}()
}
```

启动位置：

```text
backend/cmd/server/main.go
```

确保在配置初始化后启动。

## 6. 赛后补看摘要后端设计

### 6.1 数据结构

在 `backend/internal/services/ai_service.go` 新增：

```go
type PostMatchSummaryRequest struct {
	MatchID      uint `json:"match_id" binding:"required"`
	ForceRefresh bool `json:"force_refresh"`
}

type PostMatchSummaryResponse struct {
	Summary             string    `json:"summary"`
	ScoreLine           string    `json:"score_line"`
	KeyTakeaways        []string  `json:"key_takeaways"`
	QualificationImpact string    `json:"qualification_impact"`
	WorthWatching       string    `json:"worth_watching"`
	SpoilerLevel        string    `json:"spoiler_level"`
	DataNote            string    `json:"data_note"`
	GeneratedAt         time.Time `json:"generated_at"`
}
```

### 6.2 Service 方法

新增：

```go
func GeneratePostMatchSummary(ctx context.Context, req PostMatchSummaryRequest, userID *uint, ip string) (*PostMatchSummaryResponse, error)
```

校验：

- 比赛存在。
- `match.Status == "finished"`。
- `HomeScore`、`AwayScore` 不为空。

未结束时返回明确错误：

```text
post match summary is only available after match finished
```

### 6.3 Facts 构建

构建上下文时只使用本地已有事实：

- 比赛双方。
- 比分。
- 小组/阶段。
- 城市/球场。
- 当前积分榜。
- 首发阵容是否可用。
- 已有阵型。

第一版不要引用不存在的事件字段，例如：

- 进球时间。
- 红黄牌。
- 射门数。
- 控球率。
- 伤病。

Prompt 必须强调：

```text
不要编造 Facts 中不存在的进球、红黄牌、伤病、射门、控球率或新闻。
如果当前数据只有比分、阵容和积分，请明确说明。
```

### 6.4 缓存策略

复用 `AIGeneratedContent`。

类型：

```text
type = post_match_summary
target_type = match
target_id = match.id
```

缓存 key：

```go
cacheKey := fmt.Sprintf("post_match_summary:%d:%d", match.ID, match.UpdatedAt.Unix())
```

如果 `ForceRefresh = false`：

- 优先读取缓存。

如果 `ForceRefresh = true`：

- 重新生成并写入新缓存。

### 6.5 API 设计

新增 handler：

```text
backend/internal/handlers/post_match_summary_handler.go
```

接口：

```http
GET /api/matches/:id/post-match-summary
POST /api/matches/:id/post-match-summary/generate
```

`GET` 行为：

- 比赛未结束：返回 unavailable。
- 有缓存：返回摘要。
- 无缓存：返回 empty 状态。

`POST` 行为：

- 比赛结束后生成摘要。
- 支持 `force_refresh`。

示例响应：

```json
{
  "summary": "巴西 2-1 击败摩洛哥，拿到关键三分。本摘要基于当前比分、阵容和积分信息生成，未包含进球事件细节。",
  "score_line": "巴西 2-1 摩洛哥",
  "key_takeaways": [
    "巴西获得三分，小组排名形势更主动",
    "摩洛哥仍需关注后续比赛结果",
    "当前数据未包含进球时间和技术统计"
  ],
  "qualification_impact": "需要以最新小组积分榜为准。",
  "worth_watching": "看集锦即可：当前可用数据不足以判断完整比赛观赏性。",
  "spoiler_level": "full",
  "data_note": "基于本地比分、阵容和积分数据生成。",
  "generated_at": "2026-06-15T05:20:00Z"
}
```

### 6.6 自动生成 Job

新增文件：

```text
backend/internal/jobs/post_match_summary_scanner.go
```

配置：

```env
POST_MATCH_SUMMARY_ENABLED=true
POST_MATCH_SUMMARY_SCAN_INTERVAL_SECONDS=600
POST_MATCH_SUMMARY_LOOKBACK_HOURS=24
POST_MATCH_SUMMARY_AUTO_GENERATE=true
```

扫描条件：

- `status = finished`
- `home_score IS NOT NULL`
- `away_score IS NOT NULL`
- `updated_at` 在过去 `POST_MATCH_SUMMARY_LOOKBACK_HOURS` 内。
- 尚未存在可用 `post_match_summary` 缓存，或尚未发过通知。

处理流程：

1. 查询 finished 比赛。
2. 调用 `GeneratePostMatchSummary`。
3. 查询目标用户。
4. 为用户创建 `post_match_summary` 通知。
5. 写入 `UserMatchEventLog(post_match_summary)`。

AI 失败时：

- 记录日志。
- 不影响后续比赛扫描。

## 8. 测试建议

### 后端单元测试

覆盖：

- `UserMatchEventLog` 唯一键去重。
- 阵容未满 11 人不发送首发通知。
- 阵容可用时只发送一次通知。
- 比赛未结束不允许生成赛后摘要。
- AI 缓存命中时不重复调用 provider。

### 手动验证

1. 给某场比赛创建收藏或 reminder。
2. 写入该比赛双方 `match_lineups` 和 11 名首发。
3. 运行 lineup alert scanner。
4. 通知中心出现 `lineup` 通知。
5. 再运行一次 scanner，不新增重复通知。
6. 将比赛状态改为 `finished` 并写入比分。
7. 调用赛后摘要生成接口。
8. 刷新比赛详情页能读到缓存摘要。

## 9. 验收标准

### 首发阵容提醒

- 已收藏或已设置提醒的比赛，在首发阵容同步可用后收到一次站内通知。
- 同一用户同一比赛不会重复收到首发通知。
- 通知包含 `target_type = match` 和 `target_id = match.id`。
- 点击通知后前端可跳转比赛详情页。

### 赛后补看摘要

- finished 比赛可手动生成摘要。
- 摘要写入 `AIGeneratedContent`。
- 重复请求优先返回缓存。
- 自动扫描可为 finished 比赛生成摘要。
- 相关用户只收到一次摘要通知。
- 摘要不编造本地 Facts 中不存在的事件。

## 10. 推荐开发顺序

1. 扩展 `Notification`。
2. 新增 `UserMatchEventLog`。
3. 实现通知跳转所需后端字段返回。
4. 实现首发阵容提醒 service 和 job。
5. 实现赛后摘要手动生成接口。
6. 实现赛后摘要自动生成 job。
7. 补充测试。
