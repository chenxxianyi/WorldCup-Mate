# WorldCup Mate 首发阵容提醒与赛后补看摘要开发方案

## 1. 背景与目标

本项目是个人自用的世界杯助手，功能设计应优先服务个人观赛场景，不追求复杂运营能力。

本方案聚焦两个功能：

1. 首发阵容提醒：关注或收藏的比赛一旦同步到首发阵容，自动生成站内通知，可选邮件通知。
2. 赛后补看摘要：比赛结束后自动生成一份简短摘要，方便第二天快速了解比分、关键影响和是否值得补看。

设计原则：

- 尽量复用现有能力：`notifications`、`reminders`、`match_lineups`、`AIGeneratedContent`、AI service、定时任务。
- 站内通知优先，邮件作为可选增强。
- 不引入复杂消息队列，使用已有 Go 定时任务即可。
- 生成内容必须基于本地比赛、阵容、比分、积分等事实上下文，不编造事件。
- 第一期先做个人够用版本，后续再增强为更完整的比赛事件摘要。

## 3. 功能一：首发阵容提醒

### 3.1 用户场景

个人使用时，最常见场景是：

- 已收藏某场比赛。
- 已设置开赛提醒。
- 已关注某支球队。
- 比赛开始前想知道首发是否公布。

当系统同步到该比赛两队首发阵容后，用户收到通知：

```text
首发已公布：墨西哥 vs 南非
双方首发阵容已更新，点击查看阵型和首发名单。
```

点击通知后进入比赛详情页。

### 3.2 触发条件

首发提醒触发时机：

- `match_lineups` 中该比赛至少一方 `status = available`，推荐第一期要求双方都有 `start_xi >= 11` 再提醒。
- 比赛状态不是 `finished` / `cancelled`。
- 当前时间处于 `kickoff_time_utc - 120min` 到 `kickoff_time_utc + 30min`。
- 该用户对此比赛满足至少一个条件：
  - 收藏了该比赛。
  - 对该比赛设置过 reminder。
  - 关注了主队或客队。

为了个人项目简单可靠，第一期可以只对“已收藏比赛”和“已设置提醒比赛”发送通知；关注球队联动作为 P1。

### 3.3 去重策略

必须避免重复通知。建议新增一张轻量去重表：

```go
type UserMatchEventLog struct {
    ID        uint      `gorm:"primaryKey" json:"id"`
    UserID    uint      `gorm:"not null;uniqueIndex:idx_user_match_event" json:"user_id"`
    MatchID   uint      `gorm:"not null;uniqueIndex:idx_user_match_event" json:"match_id"`
    EventType string    `gorm:"size:40;not null;uniqueIndex:idx_user_match_event" json:"event_type"`
    CreatedAt time.Time `json:"created_at"`
}
```

`event_type` 建议值：

- `lineup_available`
- `post_match_summary`

唯一索引：

```text
user_id + match_id + event_type
```

这样无论定时任务跑多少次，同一用户同一比赛只收到一次首发通知。

### 3.4 后端实现

新增 repository：

```text
backend/internal/repositories/user_match_event_repo.go
```

建议方法：

```go
func HasUserMatchEvent(userID, matchID uint, eventType string) (bool, error)
func CreateUserMatchEvent(userID, matchID uint, eventType string) error
```

新增 service：

```text
backend/internal/services/lineup_alert_service.go
```

核心方法：

```go
func ScanAndSendLineupAlerts(ctx context.Context) error
func SendLineupAlertForMatch(ctx context.Context, matchID uint) error
```

扫描流程：

1. 查询临近比赛：`kickoff_time_utc BETWEEN now-30min AND now+120min`。
2. 查询比赛阵容：`repositories.GetLineupsByMatch(match.ID)`。
3. 判断是否可提醒：
   - 两队都有 lineup。
   - 两队 `start_xi` 数量都达到 11。
   - 或者第一期降低为任一队可用，但通知文案写“首发阵容已有更新”。
4. 查询目标用户：
   - 收藏该比赛的用户。
   - 设置过该比赛 reminder 的用户。
   - P1 再加入关注主客队用户。
5. 对每个用户检查 `UserMatchEventLog` 是否已有 `lineup_available`。
6. 创建 `Notification`：
   - `Type = "lineup"`
   - `Title = "首发已公布：A vs B"`
   - `Content = "双方首发阵容已更新，点击查看阵型和首发名单。"`
7. 写入 `UserMatchEventLog`。

### 3.5 定时任务

新增 job：

```text
backend/internal/jobs/lineup_alert_scanner.go
```

建议节奏：

```go
func StartLineupAlertScanner() {
    ticker := time.NewTicker(2 * time.Minute)

```

1. `lineup_syncer` 负责同步阵容。

也可以在 `SyncLiveWindowLineups` 成功后直接调用通知检查，但为了职责清晰，第一期建议独立 scanner。

通知中心增强：

建议调整：

  - `reminder`：开赛提醒

```ts
}
```

## 4. 功能二：赛后补看摘要

### 4.1 用户场景

世界杯很多比赛在凌晨。用户第二天早上打开 App，希望快速知道：

- 比分是多少。
- 这场是否值得补看。
- 对小组出线有什么影响。
- 有没有关键阵容/比分信息。

通知示例：

```text
赛后摘要已生成：巴西 2-1 摩洛哥
3 分钟了解比赛结果、积分影响和是否值得补看。
```

比赛详情页展示一个“赛后补看摘要”卡片。

### 4.2 摘要内容结构

建议第一期不要做复杂事件流，因为当前项目未必已有进球、红黄牌、射门等事件数据。第一期摘要基于已有事实：

- 比赛双方
- 比分
- 比赛状态
- 小组/阶段
- 积分榜变化，若可计算
- 赛前 AI 看点，若已有缓存
- 首发阵容，若已有

返回结构建议：

```go
type PostMatchSummaryResponse struct {
    Summary              string    `json:"summary"`
    ScoreLine            string    `json:"score_line"`
    KeyTakeaways         []string  `json:"key_takeaways"`
    QualificationImpact  string    `json:"qualification_impact"`
    WorthWatching        string    `json:"worth_watching"`
    SpoilerLevel         string    `json:"spoiler_level"`
    DataNote             string    `json:"data_note"`
    GeneratedAt          time.Time `json:"generated_at"`
}
```

字段说明：

- `summary`：100-160 字中文总结。
- `score_line`：例如 `巴西 2-1 摩洛哥`。
- `key_takeaways`：3 条以内，不能编造事件。
- `qualification_impact`：小组积分影响；不确定时写“需要以最新积分榜为准”。
- `worth_watching`：`值得补看 / 看集锦即可 / 可跳过`，附一句理由。
- `spoiler_level`：`full`，因为摘要本身包含比分。
- `data_note`：说明基于当前本地数据生成。

### 4.3 AI 生成策略

新增 AI 类型：

```text
type = post_match_summary
target_type = match
target_id = match.id
```

复用 `AIGeneratedContent` 缓存。

新增 service 方法：

```go
func GeneratePostMatchSummary(ctx context.Context, matchID uint, userID *uint, forceRefresh bool) (*PostMatchSummaryResponse, error)
```

缓存 key：

```text
post_match_summary:{match_id}:{match.updated_at}:{lineups_updated_at}:{standings_updated_at}
```

个人项目可简化为：

```text
post_match_summary:{match_id}:{match.updated_at_unix}
```

当比赛比分或状态更新后，缓存 key 自然变化。

Prompt 约束：

```text
TASK:post_match_summary
你是世界杯赛后补看助手。只基于 Facts 中提供的信息总结，不要编造进球、红黄牌、伤病、射门数据或新闻。
返回 JSON：summary, score_line, key_takeaways, qualification_impact, worth_watching, spoiler_level, data_note, generated_at。
如果 Facts 不包含事件细节，请明确说明“当前数据仅包含比分/阵容/积分信息”。
```

### 4.4 自动生成时机

新增 job：

```text
backend/internal/jobs/post_match_summary_scanner.go
```

扫描条件：

- `matches.status = finished`
- `home_score` 和 `away_score` 不为空
- `kickoff_time_utc` 在过去 24 小时内，或 `updated_at` 在过去 12 小时内
- 尚未为该比赛生成过 `post_match_summary`，或缓存已过期

个人使用建议：

- 每 10 分钟扫描一次 finished 比赛。
- 每场比赛最多自动生成一次。
- 如果 AI provider 不可用，不阻塞主流程，只记录错误。

### 4.5 自动通知目标用户

通知对象：

- 收藏该比赛的用户。
- 设置过该比赛提醒的用户。
- P1：关注主队或客队的用户。

去重：

- 使用 `UserMatchEventLog` 的 `post_match_summary`。

通知写入：

```go
Notification{
    UserID: userID,
    Title: "赛后摘要已生成：A x-y B",
    Content: "3 分钟了解比赛结果、积分影响和是否值得补看。",
    Type: "post_match_summary",
    TargetType: "match",
    TargetID: match.ID,
}
```

### 4.6 用户接口

新增用户端接口：

```http
GET /api/matches/:id/post-match-summary
POST /api/matches/:id/post-match-summary/generate
```

建议行为：

`GET`：

- 如果已有缓存，返回缓存。
- 如果比赛未结束，返回 `status = unavailable`。
- 如果没有缓存，返回空状态，不自动触发 AI。

`POST generate`：

- 登录用户或本地个人项目均可调用。
- 比赛结束后才允许生成。
- 支持 `force_refresh`。

个人项目也可以只做一个接口：

```http
POST /api/ai/post-match-summary
```

但从页面语义上，挂在 match 下更直观。

### 4.7 前端展示

新增组件：

```text
frontend/src/components/ai/PostMatchSummaryCard.vue
```

放置位置：

```text
frontend/src/pages/user/MatchDetailPage.vue
```

建议在比赛详情页比分卡片后、首发阵容前展示。

展示逻辑：

- 比赛未结束：不展示，或展示“赛后生成”禁用按钮。
- 比赛已结束但无摘要：显示“生成赛后补看摘要”。
- 已有摘要：展示卡片。
- 如果开启免剧透模式，摘要卡片默认折叠，按钮文案为“显示赛后摘要”。

卡片内容：

- 标题：赛后补看摘要
- 比分：A x-y B
- 100-160 字 summary
- 3 条 key takeaways
- 是否值得补看
- 数据说明

### 4.8 免剧透联动

如果后续实现“免剧透模式”，赛后摘要必须尊重该设置：

- 通知标题避免直接写比分：
  - 免剧透开：`赛后摘要已生成：巴西 vs 摩洛哥`
  - 免剧透关：`赛后摘要已生成：巴西 2-1 摩洛哥`
- 详情页摘要默认折叠。
- 用户点击确认后再显示比分和正文。

可以先在方案中预留，第一期不强制实现。

## 6. 后端开发步骤

### P0：通知跳转与去重基础

1. 扩展 `Notification` 模型，增加 `TargetType`、`TargetID`。
2. 新增 `UserMatchEventLog` 模型。
3. 加入 `AutoMigrate`。
4. 新增 `user_match_event_repo.go`。
5. 前端通知 store 类型增加 `target_type`、`target_id`。
6. 通知列表点击后跳转比赛详情页。

### P1：首发阵容提醒

1. 新增 `lineup_alert_service.go`。
2. 查询临近比赛与可用阵容。
3. 查询目标用户。
4. 写入 `lineup` 类型通知。
5. 写入 `UserMatchEventLog(lineup_available)`。
6. 新增 `lineup_alert_scanner.go`。
7. 在 server 启动时挂载 job。

### P2：赛后补看摘要手动生成

1. 新增 `PostMatchSummaryResponse` 类型。
2. 在 `ai_service.go` 新增 `GeneratePostMatchSummary`。
3. 构建赛后 Facts：
   - 比分
   - 比赛状态
   - 主客队
   - 小组/阶段
   - 阵容可用信息
   - 小组积分
4. 复用 `AIGeneratedContent` 缓存。
5. 新增 handler 和 route。
6. 前端新增 API、store 方法、`PostMatchSummaryCard.vue`。

### P3：赛后摘要自动生成与通知

1. 新增 `post_match_summary_scanner.go`。
2. 扫描 finished 比赛。
3. 调用 AI 生成摘要。
4. 给相关用户创建 `post_match_summary` 通知。
5. 写入 `UserMatchEventLog(post_match_summary)`。
6. AI 失败时记录日志，不影响其它任务。

### P4：体验增强

1. 免剧透模式联动。
2. 通知列表按类型展示图标或标签。
3. 首页增加“今早补看”区域。
4. 比赛列表对已生成摘要的 finished 比赛显示“摘要”入口。

## 9. 风险与注意事项

- 首发阵容同步依赖第三方数据，可能在赛前很晚才出现。
- 阵容同步任务与提醒任务之间可能有时间差，提醒延迟 1-3 分钟是可接受的。
- AI 摘要不能编造进球、红黄牌、伤病等未存储数据。
- 如果当前项目没有比赛事件数据，摘要应明确说明“当前仅基于比分、阵容和积分信息”。
- 自动生成 AI 摘要会消耗 token，个人项目可接受，但仍建议缓存。
- 如果未来开启免剧透模式，通知和摘要卡片要避免直接暴露比分。

## 10. 验收标准

### 首发阵容提醒

- 已收藏或已设置提醒的比赛，在首发阵容同步可用后收到一次站内通知。
- 同一用户同一比赛不会重复收到首发通知。
- 点击通知能进入比赛详情页。
- 比赛详情页能看到已同步首发阵容。
- `go test ./...` 通过。
- `npm run build` 通过。

### 赛后补看摘要

- finished 比赛可以手动生成赛后摘要。
- 摘要写入 `AIGeneratedContent` 缓存。
- 重复打开比赛详情页优先读缓存。
- 自动扫描任务能为已结束比赛生成摘要。
- 相关用户收到一次赛后摘要通知。
- 摘要不编造本地 Facts 中不存在的事件。
- `go test ./...` 通过。
- `npm run build` 通过。
